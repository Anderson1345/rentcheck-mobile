## 3. Unidad de trabajo: la **entrega**

Antes se trabajaba con sub-tareas muy pequeñas (un endpoint por prompt). Eso multiplicaba el contexto que se repetía en cada prompt y gastaba muchos tokens. Ahora la unidad es la **entrega**: un bloque funcional completo que se puede revisar de una sola vez.

**Tamaño de una entrega:**
- Un módulo o flujo completo de punta a punta. Por ejemplo, "el motor de pagos por período con su migración, sus pruebas y su endpoint", o "todas las pantallas de Inmuebles y Unidades de la app".
- Revisable en **30 a 60 minutos**. Como referencia: hasta unos 15 a 25 archivos tocados y como máximo **una migración de Prisma**.
- Con un criterio de "terminado" verificable: comandos que pasan y un recorrido manual concreto.
- Si una entrega necesita dos migraciones o toca backend y app a la vez, se divide en A y B. **Nunca** se mezclan cambios de backend y de app en el mismo prompt ni en el mismo commit.

**Dónde está el ahorro de tokens:**
- Las reglas permanentes del repositorio viven en `AGENTS.md` y `CLAUDE.md` dentro de cada repositorio (sección 5). La IA de programación las lee sola; el prompt ya no las repite.
- El prompt referencia los documentos por ruta y por ID (B-05, regla 21, sección 5.15) en vez de copiarlos. Para eso, los documentos de contexto se copian a una carpeta `docs/` en cada repositorio (sección 5.3).
- El usuario no pega código en el chat. Trae solo el **reporte final** de la IA de programación (formato fijo, sección 4) y, si algo falla, el fragmento puntual.
- Una sola ronda de corrección por entrega, siempre que se pueda: la revisión junta todos los hallazgos en un solo prompt de ajuste.
- Dividir una entrega grande en varias medianas suma un costo fijo (leer `AGENTS.md`, el reporte y la revisión) de aproximadamente 10 a 25 % del total; a cambio se evita una revisión que no cabe en 30 a 60 minutos y una ronda de corrección más cara.

## 4. Plantilla de prompt (la usa Claude para cada entrega)

```

## Contexto
- Repositorio: <rentcheck-backend | rentcheck-mobile>. Lee AGENTS.md antes de empezar.
- Referencias (léelas; no las modifiques): docs/<archivo>.md secciones <x>, IDs <B-xx>, reglas <n>.
- Estado previo relevante: <1 a 3 líneas>.

## Objetivo
<qué debe existir al terminar, en 2 a 4 líneas>

## Alcance
Hacer:
1. ...
No hacer (queda para <entrega X>):
- ...

## Contratos
<endpoints, forma del request y la response, o esquema de Prisma esperado — solo lo que no se puede deducir del código>

## Criterios de aceptación
- [ ] ...

## Verificación que debes correr
<lista de comandos exactos>

## Reporte final (obligatorio, en este formato)
1. Resumen en 5 líneas o menos.
2. Archivos creados/modificados (lista) + `git diff --stat`.
3. Migraciones creadas (nombre) y conteo de registros afectados si hubo migración de datos.
4. Salida final de cada comando de verificación (las últimas 30 líneas si es larga; completa si falló).
5. Decisiones que tomaste por tu cuenta y dudas abiertas.
6. Prueba manual ejecutada por ti mismo (sección 7, "Prueba manual automatizada"): los pasos que corriste contra el servidor local y la salida real de cada uno. Solo lo que no se puede automatizar (teléfono, Render, panel de Supabase) se lista como pasos para el usuario.

## Git
Rama: <feat/xx-nombre>. Un commit al final con el mensaje: "<tipo>(<alcance>): <descripción>". No hagas push ni merge.
```

Reglas de la plantilla:
- Si la entrega tiene una migración con datos existentes, el prompt pide **primero un plan corto y el conteo de registros afectados, y detenerse** hasta que el usuario lo apruebe. Solo en ese caso se hace en dos pasos. (Desde B0.3-B, cuando la migración es una copia determinista y lleva su propia verificación `DO $$` dentro del SQL, el prompt puede pedir hacerla en un solo paso y decirlo explícitamente.)
- Cuando el prompt de la app necesita un contrato del backend, la IA de programación lo lee de `docs/api/openapi.json` (Swagger exportado) o, si hace falta, abierta en la carpeta padre `Rentcheck2`, **solo para leer** `rentcheck-backend`.

## Convenciones obligatorias
- Dinero: siempre entero en centavos.
- Fechas de negocio en America/Bogota (usar la utilidad de fechas del proyecto, nunca new Date() suelto para "hoy").
- DTO: propiedades con `!`; fechas con @Type(() => Date) + @IsDate(); decimales con @IsNumber().

- Nada con valor legal o financiero se borra físicamente; los PDF se versionan.
- ArrendadorActual/InquilinoActual se exportan con `export` de TypeScript, nunca en `exports: []` de @Module.
- Tras cambiar schema.prisma: npx prisma generate.
- Errores: el filtro global responde { statusCode, codigo, mensaje, detalles?, message }; para un código propio se lanza, por ejemplo, new ConflictException({ codigo: 'CONTRATO_NO_ACTIVO', mensaje: '...' }).
- Ids de ruta: siempre con ParseIdPipe (src/common/pipes/parse-id.pipe.ts), nunca @Param('id') a secas.
- Pruebas e2e: siempre configurarApp(app) (src/configurar-app.ts), nunca useGlobalPipes a mano.
- DTOs: nunca aceptan rutas ni URLs de archivos.
- Datos de recaudo (Contrato.datos_recaudo): solo se devuelven con contrato ACTIVO; en cualquier otro estado, el campo sale en null (regla 11 del contexto).
- Escrituras que dependen de un estado previo (aprobar/rechazar un pago, confirmar una terminación anticipada, cambiar el estado de una solicitud) nunca se hacen como "leer y luego escribir": se usa `updateMany` (o una transacción interactiva `$transaction(async (tx) => ...)`) condicionado al estado esperado en el `where`, y se revisa `count` para saber si la escritura realmente ocurrió. Esto evita que dos peticiones casi simultáneas dupliquen el efecto (ver B-36, corregido en B0.1-B).
- Toda fecha de "hoy" para lógica de negocio (mora, vencimientos, estado de cuenta) usa `hoyEnBogota()` (src/common/hoy-bogota.util.ts), nunca `new Date()` suelto. Toda aritmética de fechas de negocio usa métodos `getUTC*`/`Date.UTC(...)`, nunca los métodos locales (`getFullYear`, `getMonth`, `new Date(y,m,d)` sin UTC) — los campos `@db.Date` de Prisma son medianoche UTC del día calendario, y mezclar local/UTC produce resultados distintos según la zona horaria de la máquina que corre el proceso (ver B-19, y `src/common/estado-cuenta.util.ts` desde B0.2-A).

## Prohibido

- Push, merge o force-push.

## 6. Flujo de git por entrega

1. `git checkout main && git pull` → `git checkout -b feat/<codigo>-<nombre>`.
2. Ejecutar el prompt.
3. Revisar: `git diff --stat`, abrir en VS Code los archivos clave que señala Claude y correr la verificación.
4. Si hay ajustes: un solo prompt de corrección con todos los hallazgos juntos.
5. `git checkout main && git merge feat/...` → `git push origin main`. En el backend, confirmar que Render redespliega (estado "Live"). La prueba manual ya la hizo la IA de programación en local; no se repite en producción salvo que la entrega toque datos o configuración de producción.
6. Traer a Claude el reporte final y el resultado de la prueba manual → Claude actualiza la sección 9 de este archivo.

Si se usa una herramienta alternativa (OpenHands u otra), se exige lo mismo, más confirmar en qué rama quedó el trabajo.

**Entregas que se fusionan juntas (B0.4-A1 + A2):** A1 deja que el arrendador cree contratos con cédulas nuevas y A2 hace que el portal del inquilino exija la vinculación. Fusionar A1 sola abriría una ventana en la que un arrendador podría asociar contratos a cualquier cédula sin que el portal del inquilino lo controle. Por eso A2 se construye sobre la misma rama de A1 y se hace un solo merge (mismo mecanismo de la nota siguiente sobre ramas apiladas). Producción no cambia hasta ese merge.

**Notas prácticas (agregadas tras B0.0 y B0.1):**
- En Windows/PowerShell, `&&` no encadena comandos. Cada paso de git se corre en su propia línea.
- Al terminar cada entrega, correr `git fetch origin` y `git branch -a` para ver qué ramas remotas quedaron vivas, y borrar (local y remoto) las que ya se fusionaron. Una rama vacía se detecta con `git log main..<rama> --oneline`: si no imprime nada, no tiene nada por delante de `main` y se puede borrar.
- Cuando una rama nueva se crea a partir de otra que todavía no está en `main` (por ejemplo, una tarea de apoyo creada sobre la rama de una entrega en curso), el PR de GitHub incluye los commits de las dos. No hay que abrir un PR aparte: basta con fusionar ese PR una sola vez; los cambios de ambas quedan en `main` juntos.

## 7. Listas de verificación

**Backend (toda entrega):** `npx prisma generate` → `npx tsc --noEmit` → `npm run lint` → `npm run test:e2e` (sin fallos, con la cantidad de suites y pruebas) → la prueba nueva cubre el caso del bug corregido → Swagger local (`http://localhost:3000/api/docs`, con la rama de la entrega corriendo, **nunca la URL de producción antes del merge**) muestra los DTOs con sus campos y el comportamiento nuevo → después del merge: confirmar que Render redespliega y la migración se aplica (la prueba manual se hace en Swagger local; una llamada en producción solo cuando la entrega toca datos o configuración de producción, o algo que únicamente se pueda verificar allí) → exportar `openapi.json` a la app si cambió la API.

**Prueba manual automatizada (regla desde B0.3-B, a pedido de Jesús):** la prueba manual de una entrega de backend la ejecuta la IA de programación, no Jesús. Levanta el servidor local con la rama de la entrega contra la base local de desarrollo (`npm run sembrar`), recorre los pasos de la prueba manual con peticiones HTTP reales (script `scripts/humo-<entrega>.js` o `Invoke-RestMethod`; sin tocar producción) y pega la salida real de cada paso: código HTTP y los campos que importan. Si un paso falla, lo dice y no cierra. Jesús solo hace lo que la IA no puede: pruebas en el teléfono, comprobar que Render queda en "Live" y consultas al panel de Supabase que de verdad hagan falta. Las migraciones con datos deben llevar su propia verificación dentro del SQL (bloque `DO $$` que aborta si los conteos no cuadran), de modo que el despliegue de Render falle si algo no cuadra en producción y Jesús no tenga que comparar conteos a mano.

**Migraciones con datos:** conteo antes y después; primero en `rentcheck` (local), después en `rentcheck_test`, y en producción solo después de un respaldo con `pg_dump`.

**Migraciones que agregan una restricción única o un índice único (lección de B0.3-A1):** antes del merge, comprobar en **producción** (consulta de solo lectura, en el editor SQL de Supabase) que no haya duplicados, porque `prisma migrate deploy` corre en el build de Render y un duplicado hace fallar el despliegue. En B0.3-A1 la consulta encontró 2 años duplicados en `ConfiguracionIpc` que las pruebas locales no mostraban. Si la migración cambia columnas a opcionales o agrega restricciones y `prisma migrate dev` no corre por ser no interactivo, se escribe el SQL a mano, idéntico al que genera Prisma, y se aplica con `migrate deploy`; se verifica con `prisma migrate diff` que no quede deriva y que el índice parcial `unidad_contrato_activo_unico` (solo existe en SQL) no se toque.

**App (toda entrega):** `npx tsc --noEmit` → `npm run lint` → `npx expo-doctor` → recorrido en un teléfono Android real (development build o Expo Go mientras no haya módulos nativos que lo impidan) → se llega a cada pantalla nueva **navegando**, no escribiendo rutas → probar sin internet al menos una pantalla → revisar que no haya tokens ni datos personales en los logs.

**Seguridad (entregas que tocan autenticación o archivos):** probar con un token del otro rol, con un id ajeno (debe dar 404) y con un id inválido (debe dar 404, no 500). Recordar que los guards de autenticación corren antes que los pipes de validación: sin token, un id inválido da 401, no 404; para probar el 404 hay que autenticarse primero.

**Integración entre módulos (lección de B0.3-A2, B-49):** una función pura probada por separado puede esconder un error de integración si su contrato cambia de significado (el canon base contra el vigente). Cuando una entrega cambia el significado de un campo que otros módulos leen, se listan todos los llamadores y se agrega al menos una prueba e2e que combine los dos módulos; la prueba que reproduce el error se escribe primero y se muestra fallando antes de corregir.

**Pruebas de reversión (lección de B0.4-A1, B-54):** una prueba que dice probar la reversión de una transacción debe forzar el fallo **después** de la escritura que se quiere deshacer y comprobar que esa escritura no quedó. En A1 esa prueba (i) falló y destapó que `esColisionDeCodigoAcceso` nunca detectaba la colisión con el adaptador de pg (`meta.target` no viene; el nombre de la restricción llega en `meta.driverAdapterError.cause.originalMessage`). Regla: no se lee `meta.target` de un P2002 sin probarlo contra la base real; y dentro de una transacción interactiva un P2002 la envenena, por eso se usa `createMany({ skipDuplicates: true })` y luego `findUniqueOrThrow`.

**Revisión (lección de B0.2-B):** el reporte de la IA de programación no basta. Se revisa el código real de las funciones de lógica de negocio y las aserciones de las pruebas nuevas contra el documento 1. Si una prueba "tuvo que ajustarse" para pasar, se pregunta si lo que estaba mal era la prueba o la función.
